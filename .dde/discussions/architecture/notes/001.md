# Расскажи мне больше, покажи мне архитектуру приложения остального того, что мы сейчас пишем в ModularCore архитектуре.

*Discussion: Architecture*

В ModularCore центр приложения — **единый учёт поручений, прав и результатов**. Ниже — схема по текущему коду; пунктиром показаны связи, перенос которых в ядро ещё продолжается.

```mermaid
flowchart TD
    TG["Telegram"] --> BR["Мост OpenClaw"]
    BR --> API["Локальный сокет"]
    CLI["Команды Butler"] --> API
    AM["Голос и наблюдения"] -.-> API

    subgraph CORE["Модульное ядро · butler-core"]
        API --> EV["Приём и устранение дублей"]
        EV --> TASK["Задачи и шаги"]
        TASK --> ROUTE["Маршрутизация"]

        ROUTE --> RULE["Явные команды"]
        ROUTE --> S2["System 2 · агент OpenClaw"]
        ROUTE -.-> S1["System 1 · теневой режим"]

        RULE --> OP["Операции"]
        S2 --> OP
        OP --> AUTH["Права и подтверждения"]
        AUTH --> EXEC["Исполнение через адаптеры"]
        EXEC --> CHECK["Учёт исхода и сверка"]
        CHECK --> TASK

        TASK --> DEL["Независимая доставка"]

        DB[("SQLite · события и состояния")]
        EV --- DB
        TASK --- DB
        OP --- DB
        DEL --- DB

        CFG["Персоны и конфигурация"] --> AUTH
        CFG --> ROUTE
        OPS["Диагностика и восстановление"] --- DB
    end

    EXEC --> WORK["Codex / Claude"]
    EXEC -.-> TOOLS["Инструменты и интеграции"]
    S2 -.-> MEM["Знания · vault и поиск"]
    AM --> RAW["Локальный архив наблюдений"]
    DEL --> OUT["Telegram"]
    DEL -.-> VOICE["Голосовой ответ"]
    DB --> BACKUP["Резервные копии"]
```

Главное разделение: **задача хранит намерение и прогресс, операция — конкретное действие, доставка — передачу результата**. Поэтому сбой отправки ответа не должен запускать работу повторно, а неизвестный исход действия требует сверки.
