# **Архитектурная спецификация автономной системы персонального ассистента на базе платформы OpenClaw**

## **Эволюция парадигмы систем управления искусственным интеллектом**

Исторически архитектура цифровых ассистентов и систем искусственного интеллекта строилась на основе линейной, сильно связанной модели запросов и ответов. В традиционной топологии клиент обмена сообщениями (например, бот в мессенджере) передает пользовательский запрос на промежуточный пользовательский сервер (Custom Backend), который, в свою очередь, транслирует этот запрос агенту, взаимодействующему с набором разрозненных инструментов. Данная модель неизбежно приводит к фрагментации контекста, увеличению задержек при передаче данных и создает хрупкие точки интеграции при добавлении каждого нового канала связи или функциональной возможности. Предлагаемая в данном документе архитектура фундаментально пересматривает этот устаревший подход, заменяя его концепцией единой операционной среды.  
Проектируемая система (далее — Butler) базируется на архитектуре «OpenClaw-first». В рамках этой парадигмы устраняется необходимость в разработке собственных шлюзов для Telegram или WhatsApp, собственных маршрутизаторов сессий и многоканальных коммуникационных слоев.1 Вместо этого OpenClaw выступает в роли базовой платформы, функционирующей как полноценная персональная операционная система. Поверх этого фундаментального ядра наслаиваются пользовательские плагины проектов (project plugins), система памяти на базе Obsidian (Obsidian memory), интеллектуальные модули анализа проектов и GitHub (GitHub/project intelligence), мониторинг использования ресурсов (usage monitoring) и оркестратор агентов-программистов (coding-agent orchestration).  
Платформа OpenClaw официально позиционируется как устанавливаемый на собственном оборудовании (self-hosted) шлюз для ИИ-агентов, обеспечивающий прямое взаимодействие через Discord, Signal, Slack, Telegram, WhatsApp и другие сети.1 Документация описывает Gateway как единую точку истины (single source of truth) для управления сессиями, маршрутизацией и подключениями каналов.1 Данная концептуальная модель идеально совпадает с целевым сценарием: инициация команды происходит из мобильного мессенджера, в то время как сложный агентный процесс выполняется локально на вычислительных мощностях пользователя.  
Таким образом, целевая архитектурная топология трансформируется из классической цепи Telegram Bot \-\> Custom Backend \-\> Agents \-\> Tools в следующую иерархическую структуру: пользовательский интерфейс (Telegram / WhatsApp / Slack) напрямую взаимодействует с OpenClaw Gateway. Шлюз передает управление на уровень Butler Workspace (Skills / Plugins), который делегирует задачи Project Orchestrator. Оркестратор распределяет нагрузку между исполняемыми средами (Claude Code / Codex / OpenCode / Local Tools / MCP Servers), которые, наконец, взаимодействуют с конечными источниками данных (Obsidian / GitHub / локальные директории / API мониторинга). Главный принцип системы: использование OpenClaw как готового, высоконадежного шлюза без попыток дублирования его встроенного функционала.

## **Фундаментальный уровень: Роль OpenClaw в системной архитектуре**

В новой архитектуре ответственность за управление коммуникациями, поддержание контекста и базовую маршрутизацию полностью делегируется ядру OpenClaw. Этот подход позволяет сосредоточить инженерные усилия исключительно на бизнес-логике персонального ассистента, а не на поддержке сетевых протоколов.

### **Управление каналами связи**

OpenClaw Gateway выступает в качестве единого мультиплексора входа и выхода. Система обеспечивает встроенную поддержку и обработку входящих соединений через Telegram и WhatsApp, которые являются приоритетными каналами управления.1 Архитектура закладывает возможность бесшовного масштабирования каналов связи для последующей интеграции Slack, Discord, iMessage и Signal посредством встроенных или внешних плагинов каналов (bundled channel plugins).1  
Кроме того, Gateway предоставляет локальный Web Control UI (доступный по умолчанию через http://127.0.0.1:18789/), который используется в тех случаях, когда требуется прямое управление системой с рабочей станции пользователя.1 Идея использования одного процесса Gateway, связывающего различные приложения для чата с постоянно доступным ИИ-ассистентом, устраняет необходимость запуска отдельных процессов-демонов для каждого мессенджера.1 Это значительно снижает потребление системных ресурсов и уменьшает площадь атаки. Для работы ядра требуется среда Node 24 (рекомендовано) или Node 22 LTS.1

### **Маршрутизация сессий и изоляция контекста**

Одной из самых технически сложных задач в разработке ИИ-систем является поддержание когерентного контекста при длительных беседах. OpenClaw решает эту задачу через встроенный механизм Session Routing.1 В проектируемой системе этот механизм работает по следующему алгоритму: Когда пользователь (например, Борис) отправляет сообщение "Давай займёмся AI Butler", OpenClaw Gateway анализирует метаданные отправителя, канал и время, после чего определяет текущую сессию (conversation/session). Захватив этот контекст, шлюз активирует Butler Orchestrator, который устанавливает специфический контекст проекта. Все последующие сообщения в рамках этого потока обрабатываются в строго изолированном контексте проекта "AI Butler".  
Маршрутизация сессий в OpenClaw является многомерной. Сессии разделяются на основе сложной матрицы критериев:

* **Идентификатор пользователя:** Строгое ограничение доступа на основе списков разрешенных контактов (allowFrom) для предотвращения несанкционированного использования шлюза.1  
* **Проектный контекст:** Динамическое связывание диалога с манифестом конкретного проекта.  
* **Агент-исполнитель:** Перенаправление запроса специфическому субагенту (например, переключение между режимами кодирования и исследований).1  
* **Изоляция рабочего пространства:** Физическое и логическое разделение рабочих директорий.  
* **Уровень авторизации:** Назначение политик доступа к файловой системе и системной оболочке.

## **Архитектура рабочего пространства Butler Workspace**

Сам персональный ассистент (Butler) физически и логически реализуется не как монолитное приложение, а как строго структурированный набор конфигураций рабочего пространства (workspace configs), навыков (skills), интеграций протокола MCP (Model Context Protocol) и проектных манифестов (project manifests) платформы OpenClaw.  
Идея заключается в том, что ядро OpenClaw предоставляет коммуникационную оболочку (shell), систему обмена сообщениями (messaging) и среду выполнения (runtime), тогда как Butler представляет собой внедренный «набор мозгов, правил и инструментов» поверх этого фундамента.

### **Топология директорий рабочего пространства**

Конфигурация системы локализуется в директории \~/.openclaw/workspace/butler/. Эта структура гарантирует портативность системы и ее независимость от глобальных конфигураций хоста.

| Компонент / Директория | Описание и архитектурное назначение |
| :---- | :---- |
| openclaw.json | Корневой конфигурационный файл, определяющий поведение шлюза, настройки памяти, пути загрузки навыков и политики безопасности.1 |
| skills/ | Директория, содержащая предметно-ориентированные навыки (boris-project-manager, obsidian-kb, usage-monitor). Эта папка имеет наивысший приоритет при загрузке плагинов.3 |
| projects/ | Хранилище манифестов в формате YAML (например, ai-butler.yaml, guitar-pickups.yaml). Манифесты декларируют пути к репозиториям, зависимости и контекст проекта. |
| memory/ | Локальная операционная память системы, хранящая сгенерированные сводки, индексы и активные сессии.5 |
| logs/ | Системные журналы аудита, необходимые для отслеживания действий агентов, вызовов API и изменений файловой системы.6 |
| policies/ | Декларативные правила безопасности и авторизации, определяющие, какие действия требуют обязательного подтверждения пользователя.6 |

## **Механизм плагинов на основе OpenClaw Skills**

Вместо разработки проприетарной системы плагинов, архитектура батлера полностью опирается на нативную концепцию OpenClaw Skills и конфигурацию уровня рабочего пространства.6 Навык (Skill) в экосистеме OpenClaw — это инкапсулированный пакет, представляющий собой директорию с центральным Markdown-файлом (SKILL.md), который содержит фронтматтер (YAML) с метаданными и инструкции на естественном языке, обучающие агента работе со специфическими инструментами или API.6  
Каждый крупный логический домен системы проектируется как независимый навык. Данная декомпозиция обеспечивает высокую отказоустойчивость: ошибка в модуле финансового мониторинга не нарушает работоспособность системы управления проектами. В систему закладываются следующие обязательные навыки: boris-project-manager, obsidian-kb, github-project-status, coding-dispatcher, research-digest, usage-monitor, finance-monitor и deployment-controller.

### **Анатомия навыка**

Каждый навык, размещенный в директории skills/, должен строго следовать единому формату описания и содержать исчерпывающую информацию для языковой модели. Обязательные компоненты спецификации навыка включают:

1. Описание назначения (Purpose).  
2. Список разрешенных инструментов и источников данных (Sources).  
3. Правила безопасности и границы применения (Safety).  
4. Ожидаемый формат входных команд (Input Format).  
5. Формат генерируемого результата (Output Format).  
6. Примеры использования (Examples) для контекстного обучения модели (few-shot prompting).  
7. Технические ограничения (Constraints).  
8. Политики для подтверждения действий (Confirmation policy).

В качестве эталонного примера можно рассмотреть архитектуру навыка менеджера проектов (skills/boris-project-manager/SKILL.md). Его целью является помощь пользователю в определении приоритетных задач на текущий день. В качестве источников данных навык использует локальные манифесты проектов, заметки из базы знаний Obsidian, репозитории GitHub, локальные папки проектов и отчеты о расходах API.  
Поведение навыка запрограммировано таким образом, что при поступлении команды "на чем мне сегодня сфокусироваться?", агент ранжирует проекты на основе жесткого алгоритма:

1. Срочность (urgency);  
2. Наличие приостановленной работы (stalled work);  
3. Недавние изменения в заметках Obsidian;  
4. Открытые проблемы (issues) и пулл-реквесты (PR) на GitHub;  
5. Сбои в конвейерах непрерывной интеграции (CI failures) 9;  
6. Аномалии в использовании ресурсов и затратах (usage/cost anomalies);  
7. Общая ценность для бизнеса (business importance).

С точки зрения безопасности навык менеджера проектов работает в режиме чтения по умолчанию. Для создания задач, изменения файлов проектов, коммитов кода, пушей на GitHub, деплоя и изменения ключей API требуется явное подтверждение пользователя (explicit confirmation).

### **Иерархия и загрузка навыков**

Управление загрузкой навыков осуществляется через параметр skills в файле \~/.openclaw/openclaw.json.3 Система поддерживает строгую иерархию приоритетов: навыки рабочего пространства (/skills) имеют наивысший приоритет и переопределяют навыки агента проекта (/.agents/skills), личные навыки (\~/.agents/skills), управляемые локальные навыки (\~/.openclaw/skills) и встроенные навыки (bundled skills), поставляемые с платформой.4 Это позволяет Butler Workspace безопасно заменять базовые инструменты веб\-исследований или работы с файловой системой на специализированные версии, не прибегая к форкам исходного кода ядра.8  
Особое внимание уделяется навыку github-project-status. Интеграция OpenClaw с GitHub позволяет агенту вызывать официальный интерфейс командной строки GitHub (gh CLI), фильтровать проблемы, проверять статус пулл-реквестов, отслеживать сбои CI и предлагать улучшения кода прямо из терминала без необходимости переключения контекста.9 Аутентификация осуществляется через gh auth login, что избавляет от необходимости жесткого кодирования (hardcoding) персональных токенов доступа (PAT) в конфигурации шлюза.9

## **Интеграция систем исполнения кода: Claude Code, Codex и OpenCode**

Критическим требованием к архитектуре является строгая изоляция оркестрации от непосредственного исполнения. Кодинг, компиляция и модификация файловой системы должны выполняться не самим модулем Butler Orchestrator, а через подключаемые среды выполнения агентов-кодеров: Claude Code, Codex, OpenCode или другие консольные интерфейсы (CLI) и бэкенды.  
Интеграция с этими мощными внешними инструментами обеспечивается за счет поддержки протоколов MCP (Model Context Protocol) и ACP (Agent Control Protocol), которые изначально встроены в ядро OpenClaw.10 В зависимости от задачи, система динамически переключается между двумя режимами работы.

### **Режим MCP Bridge Mode (Шлюз контекста)**

Этот режим используется в ситуациях, когда Claude Code, Codex или OpenCode выступают в роли мощных внешних вычислительных агентов, а OpenClaw выполняет функцию контекстного моста, предоставляя им доступ к контексту маршрутизированной сессии пользователя.10  
Архитектурный поток данных выглядит следующим образом: сообщение поступает из Telegram на шлюз OpenClaw. Далее шлюз инициализирует команду openclaw mcp serve. Эта команда запускает MCP-сервер через стандартные потоки ввода-вывода (stdio), а MCP-клиент (внешний агент) подключается к этому процессу.10 Мост (bridge) устанавливает соединение с локальным шлюзом OpenClaw по протоколу WebSocket. В этом режиме внешний агент (Claude Code / OpenCode) может напрямую взаимодействовать с локальной папкой проекта, при этом полностью осознавая контекст беседы, происходящей в Telegram.10 Мост предоставляет внешним инструментам доступ к специфическим конечным точкам MCP, таким как conversations\_list (список сессий), messages\_read (чтение транскриптов) и messages\_send (отправка ответа обратно в Telegram).10  
Данный режим идеально подходит для случаев, когда пользователь желает использовать Claude Code или Codex в качестве основного движка генерации кода, сохраняя при этом мобильность общения через мессенджер, и избегая создания громоздких мостов для каждого отдельного канала связи. Если в процессе работы внешний агент запрашивает разрешение на выполнение опасного действия (например, изменение системных файлов), этот запрос перехватывается мостом, транслируется в диалог Telegram как уведомление notifications/claude/channel/permission, и агент переходит в режим ожидания до тех пор, пока пользователь не отправит подтверждающую команду.7

### **Режим OpenClaw-hosted Runtime Mode (ACP)**

Второй режим применяется, когда OpenClaw самостоятельно удерживает и контролирует сессию программирования внутри своей внутренней инфраструктуры. Поток данных в этом случае направляется из Telegram к шлюзу OpenClaw, затем передается в подсистему OpenClaw ACP / Agent Runtime, которая напрямую взаимодействует с папкой проекта.10  
Этот режим активируется, когда требуется максимально нативный рабочий процесс OpenClaw без сложной внешней координации. Он позволяет снизить задержки (latency) и обеспечивает более плотную интеграцию с локальными политиками безопасности, поскольку агент исполняется непосредственно под надзором основного демона.

### **Поддержка OpenCode как предпочтительного уровня кодирования**

OpenCode официально интегрируется в систему как один из предпочтительных бэкендов для написания кода. Позиционируемый как AI-агент для работы с кодом с открытым исходным кодом, предназначенный для терминалов и IDE, OpenCode поддерживает режим множественных сессий, интеграцию с протоколом языковых серверов (LSP) и работу с различными моделями.11 Ключевым преимуществом интеграции OpenCode является возможность аутентификации через уже оплаченные аккаунты GitHub Copilot или ChatGPT Plus/Pro. Это критически важно для соблюдения системного ограничения: минимизировать сжигание баланса API-ключей (API keys) путем максимального использования уже оплаченных подписок и CLI-инструментов.

## **Модель специализированных агентов**

Современные автономные системы все чаще отказываются от концепции одного универсального (omni-capable) агента в пользу оркестрации роя специализированных модулей. Интеграция OpenCode и OpenClaw идеально ложится на требование разделения компетенций, где архитектор, кодер и тестер функционируют независимо.11  
Архитектура заменяет абстрактный "agent runtime" на сложную иерархическую модель маршрутизации:  
OpenClaw Orchestrator (или профильный Butler Skill) делегирует задачу модулю Agent Router. Роутер через Coding Backend Adapter подключается к вычислительному ядру (Claude Code, Codex, OpenCode), которое инициализирует специализированных субагентов.  
Система оперирует следующими узкоспециализированными ролями:

* **Architect (Архитектор):** Работает исключительно в режиме планирования (Plan mode). Анализирует запрос, собирает требования, консультируется с базой знаний и проектирует структуру. По умолчанию его права ограничены: любые попытки прямого редактирования файлов или вызова bash-команд блокируются.11  
* **Planner (Планировщик):** Декомпозирует сложные архитектурные решения на атомарные задачи.  
* **Coder (Программист):** Работает в режиме сборки (Build mode). Генерирует код и модифицирует исходные тексты в строго ограниченных директориях.  
* **Tester (Тестировщик):** Запускает локальные тестовые сценарии, анализирует вывод ошибок и возвращает обратную связь кодеру.  
* **Reviewer (Рецензент):** Выполняет статический анализ кода и проверку на наличие уязвимостей (Security Reviewer).  
* **Deployer (Специалист по развертыванию):** Выполняет инфраструктурные скрипты. Его действия в 100% случаев требуют явного подтверждения пользователя.  
* **Researcher (Исследователь):** Осуществляет поиск по документации и внешним базам данных для решения нестандартных проблем.

Пример работы маршрутизатора в реальном времени:

1. Запрос "Сделай архитектуру plugin system" направляется к Architect Agent (Plan mode).  
2. Запрос "Реализуй loader" делегируется Coding Agent (Build mode).  
3. Команда "Запусти тесты" активирует Test Agent.  
4. "Проверь security" инициирует работу Security Reviewer.  
5. Команда "Задеплой" передается Deploy Agent, который приостанавливает выполнение до получения явного согласия (requires confirmation).

## **Экономическая маршрутизация и оптимизация затрат**

Неконтролируемая работа автономных агентов может привести к экспоненциальному росту расходов на API из\-за зацикливаний или неэффективного расходования вычислительных мощностей больших языковых моделей (LLM).12 Для предотвращения подобных инцидентов в систему внедрена отдельная экономическая политика model\_cost\_policy. Эта политика заставляет оркестратор строго соблюдать приоритетный порядок выполнения (preferred\_execution\_order), пытаясь удовлетворить запрос наименее затратным способом.  
Установленный алгоритм маршрутизации затрат выглядит следующим образом:

1. claude\_code\_subscription: В первую очередь используются безлимитные или высоколимитные подписки на консольные утилиты.  
2. codex\_subscription: При недоступности первого варианта система переключается на корпоративные подписки Codex.  
3. opencode\_with\_existing\_login: Использование существующих авторизаций (например, GitHub Copilot).  
4. local\_models: Для простых задач форматирования, суммирования или базового поиска применяются локально развернутые модели, не требующие сетевых затрат.  
5. direct\_api\_keys: Использование прямых обращений к API провайдеров (OpenAI, Anthropic) рассматривается исключительно как резервный вариант (fallback).

Для прямого использования API (direct\_api\_keys) установлены жесткие ограничения: данный метод отключен по умолчанию (enabled\_by\_default: false), требует явного подтверждения для активации (require\_confirmation: true) и имеет жесткий программный лимит ежедневных расходов в 5 долларов США (daily\_limit\_usd: 5). Это защищает бюджет пользователя от логических ошибок агента или рекурсивных вызовов.12

## **Архитектура памяти: Гибридная модель знаний**

Адекватное функционирование ИИ-батлера требует сложного механизма управления контекстом, способного хранить долгосрочные факты без перегрузки контекстного окна модели. В архитектуре проводится жесткое семантическое и физическое разделение между канонической базой знаний и оперативной памятью шлюза.5

### **Каноническая база данных (Obsidian)**

Платформа Obsidian выступает в качестве неизменяемого источника истины (source of truth) для человеческой базы знаний. В хранилище Obsidian (vault) хранятся концептуальные описания проектов, архитектурные решения и персональные заметки. Батлер подключается к этой системе исключительно в режиме "только чтение" (read-only). Это гарантирует, что ошибки в логике LLM не приведут к удалению или искажению критически важной пользовательской информации. Файлы Obsidian остаются в нативном формате markdown, обеспечивая идеальную совместимость.

### **Оперативный индекс и персистентная память OpenClaw**

В то время как Obsidian хранит статику, встроенная подсистема памяти OpenClaw (memory) функционирует как поисковая оперативная среда (searchable runtime memory).5 Память OpenClaw по умолчанию использует формат обычного текста Markdown, что позволяет пользователю инспектировать ее без применения специализированных СУБД (например, в файлах вида memory/YYYY-MM-DD.md).5  
Процесс управления контекстом включает механизм автоматического сброса памяти (Automatic memory flush) и компактизации. Прежде чем сжать и обобщить длинный диалог, OpenClaw выполняет скрытый (silent) проход, напоминая агенту сохранить важные извлеченные факты, переменные состояния проектов и параметры активной рабочей сессии в файлы памяти.13 Эта система компактизации действует как журнал упреждающей записи (write-ahead logging) 14, позволяя агентам плавно переключаться между задачами, не теряя контекста.  
Конфигурация поиска памяти настраивается в файле openclaw.json, объединяя гибридный поиск, кэширование эмбеддингов и индексирование сессий.1 Практическая конфигурация памяти разделяет потоки:

* canonical\_source: obsidian (Только чтение).  
* runtime\_index: openclaw\_memory (Общий индекс).  
* project\_summaries:.butler/project-memory (Сводки по проекту).  
* session\_summaries:.butler/sessions (Активный контекст).

## **Модель угроз и расширенная конфигурация безопасности**

OpenClaw позиционируется как привилегированная инфраструктура автоматизации (privileged automation infrastructure). Инструмент обладает колоссальным потенциалом: он имеет доступ к мессенджерам, файловой системе, системной оболочке (shell), браузеру, GitHub и электронной почте.2 Следовательно, безопасность должна быть фундаментальной частью архитектуры, а не дополнительным модулем, который внедряется после релиза. Исторические прецеденты, такие как обнаружение вредоносных плагинов на сторонних площадках или инцидент с обнаружением 30 000 публично доступных экземпляров OpenClaw в сети интернет, подчеркивают критическую важность изоляции.14  
Базовая постулата безопасности (Default posture): **Запрещено по умолчанию, разрешено только явно (deny by default, allow explicitly)**.7

### **Изоляция и сетевые периметры**

Система должна запускаться исключительно на контролируемой рабочей станции или в выделенном облачном контейнере (VPS).12 Доступ к управлению ограничивается строгими списками разрешенных идентификаторов (allowlists) в конфигурации Telegram/WhatsApp. Категорически запрещается открывать публичный доступ к конечным точкам шлюза (gateway endpoints); для удаленного управления следует использовать технологии VPN-туннелирования (например, Tailscale).1 Доступ к папкам проектов предоставляется только через белые списки путей монтирования, ограничивая видимость файловой системы для агента. Безопасность среды выполнения требует использования контейнерной изоляции (Docker или Podman), чтобы предотвратить выход агента за пределы песочницы.8

### **Контроль учетных данных и инъекции промптов**

Все секретные ключи, токены доступа к API и пароли извлекаются из кода конфигурации и передаются через защищенные менеджеры секретов (secret managers). OpenClaw инъецирует переменные окружения исключительно на время работы агента, после чего восстанавливает исходную среду, предотвращая компрометацию ключей при записи журналов.8 Проблема инъекции промптов (prompt injection) рассматривается как реальная, нерешенная угроза на уровне индустрии.1 Навыки (Skills), загруженные из внешних источников (включая ClawHub), по умолчанию считаются недоверенными (untrusted) до прохождения ручного аудита исходного кода SKILL.md.6

### **Механизм обязательного подтверждения (Human-in-the-Loop)**

Любые деструктивные действия (destructive actions) перехватываются протоколом MCP. Выполнение команд системной оболочки (shell commands), имеющих побочные эффекты, модификация производственных баз данных, развертывание кода (production deploy) и изменение настроек биллинга блокируются подсистемой авторизации. Запрос на выполнение транслируется в контрольный интерфейс (Telegram), и агент переходит в режим ожидания до получения явного разрешения.7 Дополнительно ведется строгий аудит: система обязана вести неизменяемые журналы (audit logs), фиксирующие каждое действие агента, запрашиваемые им URL-адреса и выполненные скрипты.6

## **Стратегия внедрения: Определение MVP (Минимально жизнеспособного продукта)**

Предыдущий план создания MVP, основанный на разработке "Telegram bot", полностью упраздняется в пользу архитектуры OpenClaw. Процесс развертывания должен быть поэтапным, начиная с настройки фундаментального уровня связи и заканчивая интеграцией сложных вычислительных бэкендов.  
Обновленный план внедрения MVP включает следующие строго определенные шаги:

1. **Установка ядра:** Инсталляция и базовая конфигурация OpenClaw Gateway на выделенном сервере или локальной машине.1  
2. **Настройка коммуникаций:** Подключение Telegram в качестве основного канала взаимодействия.1  
3. **Инициализация рабочего пространства:** Создание изолированной директории Butler workspace (\~/.openclaw/workspace/butler/).  
4. **Разработка плагинов (Skills):** Написание базовых спецификаций навыков: project-manager, obsidian-kb, github-status, coding-dispatcher, usage-monitor и research-digest.6  
5. **Формализация проектов:** Разработка стандартного формата проектного манифеста (project manifest format).  
6. **Интеграция источников знаний:** Подключение хранилища Obsidian (vault) и локальных директорий с кодом в строгом режиме "только для чтения" (read-only).  
7. **Настройка версионирования:** Подключение утилиты командной строки GitHub (gh) в режиме read-only для мониторинга статусов.9  
8. **Подключение адаптеров кодирования:** Интеграция систем Claude Code, Codex или OpenCode посредством адаптера (MCP Bridge Mode).10  
9. **Реализация интерфейсных команд:** Программирование базового набора слэш-команд для взаимодействия: /projects, /project \<id\>, /status, /daily, /research \<topic\>.  
10. **Аудит и безопасность:** Внедрение базового журнала аудита (audit log) и развертывание политик оценки рисков (permission/risk policy). Внедрение жесткого правила: все операции записи в файлы (file writes), команды оболочки (shell commands), git push и процедуры деплоя выполняются только после явного подтверждения пользователя (requires confirmation).

## **Заключение**

Спроектированная архитектура описывает создание автономной персональной операционной системы на базе OpenClaw, которая функционирует не просто как оболочка поверх языковой модели (wrapper над LLM), а как глубоко интегрированный шлюз для управления жизнью и проектами. Инкапсулируя функции связи, маршрутизации и памяти на уровне Gateway, и перенося логику в декларативную систему навыков (Skills), архитектура достигает высокой степени устойчивости и расширяемости.  
Использование протокола MCP для делегирования сложных вычислительных задач специализированным агентам (Claude Code, OpenCode) 10, при сохранении контроля через единый интерфейс Telegram, решает проблему контекстного переключения. Применение многоуровневой системы безопасности с презумпцией недоверия, обязательным подтверждением деструктивных действий и строгим экономическим контролем ресурсов превращает систему из экспериментального чат-бота в надежную инфраструктуру для ежедневного использования разработчиком или менеджером проектов.
